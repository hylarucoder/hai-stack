# Hai Simplified Technical 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

让技术文档只有一种读法：一个词一个意思，一句一件事，每个动作写明谁做，要求的强弱用固定的词。规则来自 ASD-STE100 第一部分的九章。英文规则保留了 STE 里对软件文档有用的语法规则。中文规则删掉了只管英语语法的条文，补上了中文技术文档自己的毛病：包装动词（进行、加以）、长定语、省略主语、代词指代不清。

两种语言共用一套规则编号。规则全文、理由、例子和检查方法在 `references/rules-en.md` 和 `references/rules-zh.md`。

## 适用范围

**只用于技术文档**：读者读它，是为了理解一个系统、做一个操作，或者做一个技术决定。设计文档、README、API 文档、runbook、故障排查、迁移指南、提交说明、PR 描述、代码注释、错误信息和界面帮助文字，都属于这一类。

**不用于营销和创作**：营销文案、品牌故事、博客和社交媒体帖子、发布公告、演讲稿、文学写作。这些文字靠节奏、情绪和修辞打动人，套上规则会变得干瘪。遇到这类请求，照常写，不用本技能。

**混合文档**：发布说明、产品公告常常既有宣传，也有技术内容。规则只用在技术部分：改了什么、怎么升级、哪里不兼容。

用户明确要求对非技术文字用这套规则时，照做，但先提醒一句：文字会失去说服力。

## 语言

- 每部分按它自己的语言用规则。语言看文档本身，不看对话用的语言。
- 中文文档里夹英文术语，用中文规则；术语怎么写，按 9.1。
- 双语文档，两种语言各用各的规则。
- 翻译不属于本技能。用户要求翻译时，先翻译，再按目标语言的规则改。

## 流程

1. **判断范围。** 确认是技术文档。
2. **找项目约定。** 找术语表和写作规范，位置见规则文件第 10 章。项目约定和本规则冲突时，以项目为准，例如引号写法、固定译名。
3. **写或改。** 按 `SKILL.md` 的规则速览写。某条规则拿不准，或者需要例子时，读对应语言的规则文件。
4. **机械检查。** 运行 `python3 <技能目录>/scripts/check.py <文件>`，加 `--lang en` 或 `--lang zh` 可以指定语言。脚本只报出要看的地方，不做判断：引用的例子、紧挨代码名的写法、有理由保留的软规则，可以不改。
5. **交付。** 按 `references/output-template.md`。

## 规则速览

硬规则全守；软规则做到八成，不守的每一条都要有理由。完整的速览（含英文和中文的对照写法）在 `SKILL.md`。中文要点：

- **词**：一词一义，一义一词，用术语表里的词；不用适当、有关的、一定程度上、较为、基本上、若干、显著、大幅、明显；不用处理、操作、优化这类空动词。
- **名词短语**：一个名词前最多两个“的”；连着的名词不超过三个；“的、地、得”分开用。
- **动词**：不用进行、加以、予以、做出、实现了对……的；用主动句；陈述事实不用“正在”；写要求只用应 / 不应 / 宜 / 不宜 / 可 / 不必。
- **句子**：一句一事；主语换了就写出来；代词只指一个东西；用因为、所以、如果、但写明关系；三项以上用列表。
- **步骤**：编号列表，一步一条指令，动词开头，条件在前，每句不超过 40 字，结果单独写。
- **说明**：结论在段首，一段一个主题，每句不超过 50 字，数字写明条件和日期，分清已做和计划。
- **警告**：放在步骤前；先写指令再写后果；分“警告”和“注意”两级。
- **标点和写法**：全角标点，全文一种引号，中文和英文、数字之间空一格，范围用“–”，代码名放在反引号里，不用开箱即用、无缝、赋能这类套话。

## 不要过度

规则是为了让读者读得准，不是为了把文字写成电报。

- **八成有界限。** 硬规则全守。软规则在会让句子别扭或丢信息时，可以不守。
- **规则管说法，不管内容。** 原文的事实、条件、例外和不确定都要保留。原文缺了读者需要的东西（风险、回退办法、缓存过期），照样指出来，写成说明或待确认问题。
- **改写不是审计。** 作者的说法按原来的强度保留，只删空的程度词（“显著提升” → “提升”，“等若干核心服务” → “等核心服务”）。不在文中要求文档自证；缺的证据在交付说明里列给作者，见 `references/output-template.md`。
- **文中的占位符要少。** 只有读者缺了这个信息就做不了事时（设哪个参数、查哪个 key），才在文中写“[待补：……]”。不把猜测的值写进占位符，也不编一个看起来合理的数。
- **该留的不动。** 引文、代码、命令输出、专有名词、用户原话照原样保留。
- **保留结构。** 句子可以重排；章节、标题、链接不动，除非用户要求。

## 什么时候用别的技能

- 文档内容过时，要按核实过的结论重建：用 `hai-rewrite-doc`。重建后需要改措辞，再用本技能。
- 要判断文档对不对、和代码是否一致：用 `hai-audit-docs`。
- 只是 Markdown 排版有问题：用 `readme-beautifier`。
- 要定一个跨模块概念叫什么：用 `hai-naming`，结果记进术语表。
- 要写或调整 PRD：用 `hai-prd`。之后可以用本技能改措辞。

## 常见错误

- 把规则用在营销文案上，把文字写干。
- 把每个没有数据的说法都改成文中的 [待补]，文档变成了缺口清单。缺口报告给作者，文档保持可读。
- 在占位符里写猜测的值，或者写一个看起来合理的数字。
- 为了句子短，删掉了注意事项或风险。
- 为了守 1.4 或 9.4，改掉了正确的技术术语。
- 把脚本报出的每一处软规则都当成缺陷。
