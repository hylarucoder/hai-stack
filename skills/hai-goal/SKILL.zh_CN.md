# Hai Goal 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

> 触发：在真正执行前先产出一份 goal document——可验证目标、边界、当前状态、分阶段路线、各阶段规则、带 proof 的 todo、dry-run，以及一个 Go / No-Go 判断，而不是一边写一边看能不能跑通。当用户想开始、go、实现、上线、构建、往前推；给了一个模糊意图需要变成具体目标；要求把工作拆成阶段或 todo；或者丢出一份已有计划加一个目标、要求围绕该目标重写并重新锚定时使用。即使用户没说"目标"或"计划"也要触发：开始干、开搞、我们开始吧、先别急着写代码先定个目标、把这个拆成阶段、拆 todo、落地方案、执行计划、怎么落地、立个目标、围绕X重新规划、重写这个计划、"lets just ship this"、"gonna start building now"，或只是贴一句意图说"做吧"，都先写 goal document。要先判断这件事到底值不值得做，再决定要不要立目标，请用 hai-idea。

## 概览

在有意义的执行之前用这个 skill，先写出 goal document，制止"一边跑一边看"。Goal document 是一个以目标为中心的具体计划：定义什么应该变成真、如何分阶段、每个阶段有什么规则、如何验证完成。它也处理第二种常见情况——用户已经有计划，但指定了一个目标并要求围绕该目标重写：保留有用内容，删除局部噪音，重排优先级，产出更强的 goal document。

## 核心原则

先写 Goal，再 Go。

不要一上来写代码、改文件，或边探索边指望执行过程中目标自己变清楚。这个 skill 存在就是为了制止"一边跑一边看"的失败模式，它长这样：

- 目标还没稳定就开始实现。
- 做到一半才发现关键决策没定。
- 修局部问题，而不是塑造整条路线。
- 让阶段边界意外地"长出来"。
- 忘了定义什么算完成。
- 把验证当成事后才补的东西。

大多数工作都应该先写成一份包含可验证目标、边界、阶段、规则、todo、依赖和 proof 的 goal document。当已有计划存在时，目标优先于旧计划的形态。

## Goal Document（目标文档）

Goal document 是一份可执行的计划，它要回答：

- **Target（目标）**：我们要让什么变成真？
- **Boundary（边界）**：包含什么、排除什么、有意延后什么？
- **Current state（当前状态）**：现在有什么，已知约束和风险是什么？
- **Route（路线）**：哪些阶段能到达目标？
- **Rules（规则）**：每个阶段受什么约束或工作约定管辖？
- **Todos**：每个阶段有哪些具体任务？
- **Verification（验证）**：如何证明每个阶段、以及整个目标，已经完成？
- **Stop conditions（停止条件）**：什么时候该暂停、提问或修订计划？

精确的输出形态——包括只在重写时填的条件段落——在 `references/output-template.md`。定稿前先读它，不要在这里重新推导字段清单。

全新 goal document 和计划重写共用同一个模板；重写时额外填 **Plan Rewrite Notes** 和 **Drift Diagnosis** 两段（见步骤 4）。

## 工作流

这一条序列覆盖所有情况——把模糊意图变成目标、为已知目标编排阶段、围绕目标重写已有计划。只有当用户给了已有计划时才执行步骤 4。

1. **冻结意图。** 用户想开始什么？什么结果值得做？什么不能破坏？还有什么未知？
2. **让目标可验证。** 把模糊活动改写成结果目标。定义边界（包含、排除、延后）。选择最强的可用证据来源——test、metric、review、artifact、command、behavior、user signal 或 trace——并给出清晰的通过/失败规则、置信度说明，以及明确的判定主体——谁或什么有权宣布完成。有用时量化，但不要编造假指标。若一个意图里含多个目标，拆开。
3. **转成 goal document。** 记录假设和未决问题，识别影响面（docs、code、schema、API、UI、tests、workflows、links），定义"可执行"意味着什么。
4. **若是重写已有计划，围绕目标重新锚定。** 抽取计划里的阶段、todo、假设、依赖和重点。诊断漂移——目标漂移、阶段漂移、验证漂移、兼容性漂移、清理漂移——逐项决定保留、重排、合并或删除。把高风险、高不确定、高杠杆的工作往前移，除非依赖不允许。旧措辞只在新目标下仍然准确时才保留。
5. **拆阶段。** 每个阶段应产出一个可评审的状态。按学习、降风险、用户可见价值、系统边界、依赖顺序、垂直切片、决策边界或验证边界切分——绝不按部门、文件类型、随意的时间顺序或标题切分。避免只写"实现 X"却没有 proof 的阶段。
6. **定义阶段规则。** 每个阶段说明：允许什么、明确暂不允许什么、适用什么兼容/迁移规则、需要什么文档更新、过关前必须通过什么验证。可借用的具体范式：
   - 目标文档没更新前不许碰实现。
   - 本阶段可直接重命名内部调用方；除非存在公开契约，否则不加兼容垫片。
   - 本阶段只能改 docs 和 tests，不能改生产代码。
   - 本阶段只有当命令/测试/检查通过时才退出。
   - 若某个 todo 需要 goal document 里没有的产品决策，停下。
7. **创建带 action + surface + proof 的 todo**（见模板）。让它们具体到不用猜就能执行，标注影响顺序的依赖和阻塞，除非阶段目标要求，否则把无关清理排除在外。
8. **dry-run 路线。** 按顺序"走"一遍阶段但不真正执行；找缺失前提、循环依赖、模糊 todo 和未验证假设；在任何真实工作之前修订 goal document。这一步正是 goal document 区别于泛泛规划的地方。
9. **决定要不要 Go。** 若路线自洽，可以开始执行。若带着未决决策，先用对应的 skill 解决（见下），再重跑 dry-run。

## 输出

返回一份 goal document，而不是泛泛建议。内联骨架（每一段都在 `references/output-template.md` 里填）：

```markdown
# Goal Document: <work name>
## Go / No-Go            — Go / No-Go / Go after decisions，附理由
## Target Outcome
## Goal Definition       — 边界、非目标、延后、验证规则、证据来源、通过标准、置信度说明、判定主体（谁/什么有权宣布完成）
## Current State
## Plan Rewrite Notes    — 仅重写场景
## Drift Diagnosis       — 仅重写场景
## Priority Rationale
## Assumptions and Open Decisions
## Phases                — 每阶段：目的、进入条件、阶段规则、todos（action/surface/proof/depends-on）、退出证明、停止条件
## Dry-Run Findings
## Final Validation
## First Execution Step
```

定稿前先读 `references/output-template.md`。全新 goal document 时省略 **Plan Rewrite Notes** 和 **Drift Diagnosis**。

## 何时改用别的 skill

- **hai-idea** —— 还不清楚这件事到底值不值得做。先验证或砍掉想法，再花力气写 goal document。
- **hai-prd** —— 路线里有未决的产品或范围决策。先把需求定了，再回来写目标。
- **hai-architecture** —— 路线里有未决的结构或边界决策。先把设计定了，再回来。
- **hai-tdd** —— 某个阶段已经可以实现了。Goal document 交棒给每个阶段内部的测试驱动执行。

## 这个 skill 不是什么

- 不是脱离行动的泛泛规划——这里的"计划"是一份可运行的 goal document，必须可执行。
- 不是项目管理日历。除非用户要，否则日期和负责人都是可选的。
