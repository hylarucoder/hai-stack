# Hai Goal 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

当执行目标模糊、跨多个有意义阶段、风险较高，或用户明确要求目标/计划/阶段/todo 时，先写一份可验证的 goal document。小任务如果结果与验证方式都清楚，就直接执行，不额外制造规划仪式。

本 skill 也负责围绕新目标重写已有计划：保留仍然有用的部分，删除局部噪音，重新安排优先级。

## 核心原则

先写 Goal，再 Go——但只在工作确实需要目标文档时。不要一边实现一边等目标自己变清楚；也不要让一个明确的小改动先填满一份大模板。

Goal document 要回答：

- 结果：最终什么应当变成真？
- 边界：包含、排除和延后什么？
- 现状：已有事实、限制与风险是什么？
- 路线：哪些阶段能形成可审查状态？
- 规则：每阶段允许与禁止什么？
- Todo：具体动作、影响面和 proof 是什么？
- 验证：谁或什么有权宣布完成？
- 停止条件：什么时候应暂停或改计划？
- 进度管理：只有跨阶段/跨会话时，如何保持 checklist 当前？

完整格式在 `references/output-template.md`。

## 工作流

1. **冻结意图。** 明确用户真正想实现的结果、不能破坏的东西和未知项。
2. **让目标可验证。** 把活动描述改成结果，写清边界、证据来源、通过规则、置信度与完成判定主体；不编造假指标。
3. **记录现状。** 写假设、待决策事项，以及受影响的文档、代码、schema、API、UI、测试或流程。
4. **已有计划时重新锚定。** 找出 goal、phase、validation、compatibility、cleanup drift；逐项判定保留、重排、合并或删除。
5. **按学习、风险、价值、边界、依赖或验证拆阶段。** 不按部门、文件类型或任意时间顺序拆。
6. **定义阶段规则。** 写清允许/暂不允许的动作、兼容和迁移约束、文档更新，以及进入下一阶段前必须通过的 proof。
7. **Todo 使用 action + surface + proof。** 标记真正影响顺序的依赖和 blocker，不夹带无关清理。
8. **仅在跨阶段或跨会话时添加进度管理。** 阶段只有 exit proof 通过后才能完成；改优先级要记录原因。
9. **Dry-run。** 不执行，只按顺序走一遍，找缺少前置、循环依赖、模糊 todo 和未验证假设。
10. **Go / No-Go。** 路线完整才 Go；仍有产品或架构决策时先交给相应 skill。

## 输出

使用 `references/output-template.md`，只保留适用章节：新目标不需要 Plan Rewrite Notes，短计划不需要 Progress Management。输出必须是一份可执行、可验证的 goal document，而不是泛泛建议。

## 路由

- 事情是否值得做：`hai-idea`。
- 产品边界或验收未定：`hai-prd`。
- 模块边界或结构未定：`hai-architecture`。
- 已进入可验证行为实现：`hai-tdd`。
- 重写的不是计划/目标文档：`hai-rewrite-doc`。

## 执行交接

阶段已经明确且用户要求实施时，继续完成改动和适量验证，不停在计划交付。可测试行为使用
`hai-tdd`；结构、配置、样式改动用编译、已有测试和针对性运行检查。完成后用
`code-review-and-quality` 审查变更，`write-technical-acceptance-report` 按风险证明目标
（低风险使用简版），复用本轮已有证据，不无理由重复检查。
