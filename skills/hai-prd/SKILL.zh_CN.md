# Hai PRD 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 概览

用这个 skill 处理所有 PRD 相关问题：是否需要 PRD、PRD 应该多大、一个需求该拆还是合、从想法写成 PRD、以及打磨已有 PRD。

PRD 不是默认产物。不是每个想法、字段、接口、配置或技术决策都需要 PRD。PRD 应该服务产品判断：谁要完成什么、为什么现在要做、边界在哪里、验收如何证明。

## 核心原则

先判断是否需要 PRD，再写 PRD。

- PRD 是产品论证，不是功能清单。
- PRD 粒度应按用户心智和可独立验收来切，不按技术层、团队或文件切。
- 一个 PRD 通常应该有一个清晰目标、一个主要用户旅程或产品边界，以及可验证验收。
- 现有 PRD 要当成系统来打磨：目标、范围、行为、验收、风险和 rollout 必须一致。
- 如果 PRD 边界错了，先拆、合或重定边界，再修局部文字。

## 四种模式

### Need PRD：是否需要 PRD

先判断产物类型。用户/业务行为变化、范围对齐、验收标准和产品风险需要记录时，才倾向 PRD。否则可能更适合 `hai-goal`、design doc、任务说明或文档审计。

### Design PRD：从 0 写 PRD

收集上下文，框定用户、问题、目标和非目标，设计范围，按场景定义行为和可观察验收。

### Craft PRD：打磨已有 PRD

通读全文，诊断目标漂移、范围漂移、冲突漂移、验收漂移、方案漂移和局部编辑漂移，再决定保留、重组、拆分、合并或重写。

### Scope PRD：拆分/合并/粒度判断

用六维测试判断：Press Release、Independent Value、Independent Acceptance、Domain Language、User Journey、Time Appetite。

不要按技术层、CRUD 或团队拆 PRD。优先按用户旅程阶段、核心路径 vs 增强、用户角色、风险复杂度、平台渠道来切。

## 输出要求

根据任务选择模板：

- Need PRD：给出产物判断。
- Design PRD：输出 PRD 草案。
- Craft PRD：输出文档级诊断和修复。
- Scope PRD：输出六维测试、拆合建议和边界。
