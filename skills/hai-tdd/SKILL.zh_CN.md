# Hai TDD 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

对真实、可验证的行为改动执行红—绿—重构，并记录失败 RED、最小 GREEN、重构决定与验证命令。用户明确要求测试先行、增加/修复行为或需要回归保护时使用。

文档、配置、样式、改名、移动包、删除字段或其他纯结构变化不要硬套 TDD；如实使用编译、已有测试、静态检查和运行验证。

## 核心原则

先红，再绿，再重构。RED 必须因为目标行为尚不存在而失败，不是因为测试写坏、导入错误或环境没装好。已经存在的行为如果让测试立即通过，不要破坏测试制造 RED；判断这是错误复现不准、行为已存在，还是 tests-after/regression 工作，并如实标记。

## TDD 不适用时

以下情况直接选择非 TDD 验证，无需为了流程向用户暂停请示：

- 一次性 prototype/spike，或当前任务只是阅读诊断。
- 纯配置、文案或样式。
- 暂时没有合理的自动验证方式。
- 纯结构调整，没有行为层面的合法 RED。

只有验证方式会实质改变用户要求或范围时才询问。

## 禁止假 RED

不要为了让结构重构看起来像 TDD 而添加：

- 一次性 AST/regex/reflection 源码扫描。
- 检查源码形状而非长期行为/策略边界的白盒 guard。
- 重复编译器工作的测试，除非仓库本来就长期维护这类 policy test。
- 只为改名、包移动、alias 或可见性调整服务的临时回归测试。

架构/static boundary test 只有同时满足三项才合理：这是长期策略、能抓住未来真实回归、并且用户明确要求或项目已有该测试模式。

## 工作流

1. **定义最小行为。** 写 input、output、副作用、边界与失败条件；只有结构变化时转成非 TDD 验证。
2. **RED。** 先写一个行为测试，优先公共 API、用户可见行为或稳定契约；只有外部系统、时间、网络、随机性等边界需要时才 mock。
3. **确认 RED。** 跑最小命令，证明失败原因正是缺少目标行为。立即通过时重新分类，不制造失败。
4. **GREEN。** 只写让当前测试通过的最小实现，不夹带未来功能和无关重构。
5. **确认 GREEN。** 先跑目标测试，再按风险扩大到模块或全量测试。
6. **REFACTOR。** 绿灯后才整理命名、重复、结构或边界，并重新运行测试。
7. 下一个行为重新从 RED 开始。

## 输出

使用 `references/output-template.md`。有合法 RED 时填写真实 RED/GREEN/REFACTOR 证据；没有时使用 No Legitimate RED 路径，不用“测试通过”一句话冒充过程。

## 路由

- 工作太大、目标和阶段不清：`hai-goal`。
- 争议是模块边界：`hai-architecture`。
- 先判断功能是否值得做：`hai-idea`。
- 只是在选名字：`hai-naming`。
