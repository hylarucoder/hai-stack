# Hai Audit Docs 中文版

执行规则以 `SKILL.md` 为准。

## 原则与模式

文档自洽不等于事实正确；当前代码也不自动推翻已批准需求。先按主张声明权威来源，再判断应该修哪一侧。

- 内部模式：只比较指定文档集合，遵守“不要看代码”。读取 `references/internal-audit.md`。
- 实现/契约模式：当前行为对照代码与配置，目标行为对照批准规格，读取 `references/checklist.md`。
- 综合模式：请求涉及两者时复用同一主张表，不重复报告。缺代码就标未验证。
- 只审查：交付发现，不修改。
- 检查并修复：用户已要求修复时，直接修有证据的指定本地文档并复查；不擅自改实现。未决产品问题单列，继续能独立完成的修复。

## 工作流

1. 明确范围、读者、场景和是否要求修改。指定文件不扩成整个目录。
2. 提取行为、命令、默认值、状态、权限、术语、验收和链接，按主张记录来源优先级。
3. 审内部冲突；没有证据不等于已经过时或错误。
4. 按场景双向检查文档与实现，标清生成源和权威源，引用双方位置。
5. 分类为文档缺陷、实现缺口、内部冲突、待证据/决策。未来规格不能被现有代码覆盖。必要时读取 `references/worked-examples.md`。
6. 给更新、移动、合并、删除、拆分或待决建议；区分建议与已执行。
7. 已授权修复则执行并复查；全文重建交给 `hai-rewrite-doc`，产品塑形交给 `hai-prd`，计划调整交给 `hai-goal`。
8. 用 `references/output-template.md` 交付范围、发现、实际修改、验证和未决项。

严重度按实际影响分 P0-P3，不因出现安全关键词机械升级；未验证项不计为确认缺陷。
纯排版用 `readme-beautifier`，字段归属用 `entity-model-auditor`，软件交付证明用
`write-technical-acceptance-report`。文档检查不能代替运行验收。
