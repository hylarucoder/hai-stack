# Hai Debug 中文版

执行规则以 `SKILL.md` 为准。状态：试用，尚未证明能在代表性真实任务中稳定提高效果。

## 原则

解释必须覆盖现象，并能预测可证伪的检查。看起来合理的补丁不是根因证据。

## 工作流

1. 明确预期、实际、范围、时间、环境/版本和请求是诊断还是修复。先读已有日志、代码、变更、测试。
2. 优先在隔离本地环境复现，记录输入、前提、命令、实际结果。偶发现象采用有界重复，记录时序和并发。
3. 沿调用、状态/配置、持久化、外部边界追踪，比较成功与失败样本，区分观察、假设和历史记录。
4. 提出少量竞争假设，逐项给支持/反证和能区分原因的低成本检查。显而易见的问题不强凑表格。
5. 执行最有信息量的安全检查，更新置信度。仅诊断时不改用户代码，可使用独立临时复现；
   已要求修复时可添加局部诊断信息。
6. 给出“前提 → 错误决策/状态 → 现象”的因果链和真实引用。无法复现则根因未确认，说明缺失证据和下一检查。
7. 仅诊断就交付原因及修复/回归建议；已要求修复则继续完成最小完整修复和验证。适合时用
   `hai-tdd`，否则诚实记录集成或运行检查，再复查原始失败与邻近契约。
8. 使用 `references/output-template.md`，区分缓解与根治、已执行与拟执行。

## 边界

不因排障擅自执行破坏性生产操作、付费调用、对外消息或压力流量。重复检查没有新信息时改变
假设或证据来源，缺资料则写清具体阻塞。不盲加重试、吞错或顺手大重构。仅清理自己创建且已经
完成用途的临时诊断内容，保留用户工作。

原因已知的行为实现交给 TDD 或常规执行；没有故障的架构复杂度交给 `hai-architecture`；
变更审查交给 `code-review-and-quality`；完整验收交给 `write-technical-acceptance-report`；
复杂执行拆分交给 `hai-goal`。
