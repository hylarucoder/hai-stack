# Hai Complexity 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

从系统真实的运行方式出发，解释一个仓库或大型子系统为什么难以修改。它把目录与包所有权、依赖方向、运行入口、核心调用链、状态与配置流、测试保护串成一张有证据的复杂度风险图。

它不是更大号的 `hai-architecture`：本 skill 负责全仓或大子系统的运行链审计；一个明确模块边界、拆合或所有权决策交给 `hai-architecture`。

## 入口模式

- **关键词入口**：从用户给出的术语、错误、模块或症状开始，向上追到所属工作流、所有者、运行链、状态/配置和测试。
- **全局入口**：先看仓库拓扑、manifest、入口和测试根，再收敛到最重要、最常改的一到三条运行链。

关键词只是线索，不是审计边界；全局审计也不是平均阅读每个文件。

## 证据闸门

一个有效 finding 至少连接下面五类证据中的三类：

1. 仓库结构或包所有权。
2. 依赖方向。
3. 运行入口与调用链。
4. 跨模块状态、配置或数据流。
5. 能保护或无法保护这条链的测试与验证。

每个引用的文件都要实际阅读；声称调用链前先追 caller/callee；判断配置或分层前先看 manifest/config；推断必须明确标记。文件大或抽象别扭本身不构成系统复杂度 finding。

## 工作流

1. 明确全仓或大型子系统范围，选择关键词或全局入口。
2. 画出主要包、manifest、构建/配置、测试根和已有边界声明。
3. 找到服务器、路由、CLI、worker、job、脚本等真实运行入口。
4. 追踪一到三条核心路径，直到领域逻辑、状态/配置、持久化或外部副作用，以及测试。
5. 只选 `references/lenses.md` 中与路径相关的镜头。
6. 找出 change amplification、认知负担和 unknown unknowns 聚集的复杂度中心。
7. 对重要问题比较保守修复与更干净的边界；只有真实迁移风险存在时才加分阶段方案。
8. 按 `references/output-template.md` 交付证据图、finding、保留项、成本、顺序和停止条件。

## 严重度与成本

- **P0**：隐藏复杂度可能导致正确性、数据、安全或可运维风险。
- **P1**：核心路径有高改动放大或未知风险。
- **P2**：边界漂移或认知负担明显拖慢日常开发。
- **P3**：只值得在顺手修改该区域时清理。

成本用 S（局部）、M（跨边界或测试）、L（所有权、公共契约、持久化或发布迁移），并解释投入是否值得。

## 路由

- 单个架构决策：`hai-architecture`。
- SSOT 漂移：`hai-ssot`。
- 文件/函数级代码整洁：`clean-code-reviewer`。
- 单个 React 组件：`react-component-diagnosis`。
- 把结论变成执行计划：`hai-goal`。
