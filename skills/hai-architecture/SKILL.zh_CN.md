# Hai Architecture 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

用 APoSD / Ousterhout 的复杂度视角，审查既有架构或指导一个明确的设计决策。先找到 change amplification、认知负担或 unknown unknowns 聚集的边界，再推荐能让系统更易理解、更易修改的结构动作。

## 选择模式

- **全局调查**：系统难改但边界不清，或涉及全仓/大子系统。读取 `references/global-audit.md`，先映射入口族，再追一至三条重要运行链，覆盖状态、配置、外部作用和测试保护。结论至少连接所有权、依赖、入口调用链、数据流、测试中的三个证据锚点。
- **局部审查/设计**：已经明确模块边界或设计决策，执行下方工作流。
- 全局调查可以自然收敛为局部决策，复用证据，不要求用户选择内部模式，也不重复两份完整报告。
- 未解释的实际故障交给 `hai-debug`；代码变更评审交给 `code-review-and-quality`。

## 证据闸门

提出架构判断之前：

1. 本次会话实际读过所有引用文件，并给出真实 `file:line`。
2. 声称调用链或改动半径前，追踪 caller 和实现，并说明搜索依据。
3. 阅读 ADR、依赖规则、架构测试和公共契约，理解团队声明的目标边界。
4. 先比较模块公开接口与真正隐藏的复杂度，再判断深浅。
5. 推断明确标记为未验证，不伪装成证据。

一条编造的 finding 比漏掉几条更伤信任。宁可找准一个有证据的复杂度中心，也不要堆满看起来合理的 smell。

## 核心判断

### 找到最痛的中心

先明确本次审查的边界或调用链。检查一个常见改动是否跨越多个所有者，是否要求同时理解多层知识，是否混合生命周期、持久化与执行责任，或者让人无法预测还要改哪里。局部命名和样式只有在暴露更深层结构问题时才进入架构结论。

### 深模块优先

好模块用小而稳定的接口隐藏大量相关复杂度。不要因为文件长就拆，也不要因为文件相邻就合：新边界能隐藏信息才拆；两边共享隐性知识、总要一起理解才合。

审每一层或新数据形状时问：

- 调用方是否真的知道得更少？
- 这一层是否拥有规则或不变量？
- 是否让非法状态更难表达？
- 下游变化能否止步于此？
- 转换是否增加了新语义、约束或所有权？

如果全是否，它大概率只是 pass-through 税。数据经过一个函数，不足以证明需要新 shape。

### 比较真实选项

非平凡决策至少比较两个实质不同的方案。当前设计、继续拆分、合并、泛化抽象只要合理，就要说明为什么不选。关键建议补一个简短红队误用、蓝队防御和剩余风险。

需要完整 lens、错误边界、复杂度词汇或红蓝细节时读取 `references/principles.md`。

## 工作流

### 审查既有代码

1. 写清边界与审查规模。
2. 通过证据闸门：读实现、调用方、契约、测试和相关决策。
3. 画出参与者/模块、依赖或状态流、目标隐藏边界的简图。
4. 找到最高杠杆的复杂度中心。
5. 只选择 `references/principles.md` 中相关的 lens，不默认逐项打分。
6. 应用深模块和层成本测试。
7. 检查 `references/red-flags.md`；困难 finding 或误报用 `references/worked-example.md` 校准。
8. 按影响排序，产出与规模相称的报告。

### 指导设计决策

1. 明确目标、边界、现有限制与必须保留的真实契约。
2. 提方案前先画当前链路。
3. 设计至少两个本质不同的方案。
4. 比较业务适配、边界清晰度、模块深度、迁移成本、运行风险和未选方案。
5. 推荐一个方案，说明剩余风险和首个证明点。

## 规模

- **Quick**：一个明确问题，给图、结论、证据、主要权衡和下一步。
- **Standard**：一个包或一条调用链，使用完整 Markdown 模板。
- **Full**：用户明确要求多个边界的完整审计。先广泛映射，再收敛复杂度中心。

任何规模都要过证据闸门。小问题不做成大仪式，全仓审计也不能只读一个显眼文件。

## 输出与路由

全局调查使用 `references/global-output-template.md`，保留入口族覆盖、调用链、状态/配置与测试证据。局部标准/完整审查使用 `references/output-template.md`；快速回答保留关键决策字段，不输出空章节。用户明确要 HTML 时再读取 `references/html-report.md`。Go 与 TypeScript 专项参考分别在 `references/go-patterns.md` 和 `references/typescript-patterns.md`。

- 单个 React 组件：`react-component-diagnosis`。
- 局部 code smell 或命名：`code-review-and-quality` / `hai-naming`。
- 产品需求：`hai-prd`。
