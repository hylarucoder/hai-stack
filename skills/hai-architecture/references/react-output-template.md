# React 组件诊断输出模板

用于输出组件架构体检报告，按组件规模裁剪。每个评分必须由具体代码证据（`file:line`）支撑——找到具体问题才扣分，给 5 分也要有值得学习的设计模式作证据。

```markdown
# 组件诊断报告：<组件名>

> <一句话概括组件职责>

## 评分卡

| 维度 | 得分 | 一句话评价 |
|------|------|-----------|
| 使用者 API | ★★★★☆ | <summary> |
| 数据流 | ★★★★★ | <summary> |
| 可测试性 | ★★★★☆ | <summary> |
| 可扩展性 | ★★★★☆ | <summary> |
| 性能 | ★★★☆☆ | <summary> |
| 心智模型 | ★★★★★ | <summary> |
| 边界契约 | ★★★★☆ | <summary> |
| **综合** | **★★★★☆ (4.1)** | <overall> |

（★ 对应 1-5 分：5 有具体模式值得在本项目复用 / 4 扎实有小瑕疵 / 3 可用但有明确改进空间 / 2 问题突出 / 1 核心职责需要重大调整）

## 逐维度分析

每个维度列出优点和不足，引用具体代码位置（`file:line`）。
不足要说清"是什么"和"为什么是问题"，而不是笼统的"可以更好"。

证据不足的维度标记未验证，不强行打分；综合分仅在七项证据充分时计算。一个根因只在主维度扣分。

## 亮点

只列出有证据的具体设计亮点，引用代码位置。这些是值得在团队内推广的模式。

## 改进建议

按优先级分三级：

### P0 — 值得尽快改
会导致 bug、性能问题、或维护隐患的问题。

### P1 — 建议优化
改了会明显提升代码质量或开发体验。

### P2 — 锦上添花
有则更好，不改也不会出事。

每条包含：
- **问题**：具体描述，引用代码位置（`file:line`）
- **影响**：这个问题会导致什么后果
- **建议**：怎么改，给出具体方向（但不写代码）
- **工作量**：S（局部）/ M（跨组件或测试边界）/ L（改变公共 API、状态所有权或迁移路径），并说明依据

## 结构决策与首个证明点

非平凡建议比较实质不同的选项，说明未选原因、主要权衡、剩余风险与首个验证。

## 架构图（可选）

如果组件有多层结构，用文本图或 mermaid 画出数据流。
```
