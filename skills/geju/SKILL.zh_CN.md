# Geju 中文版

本文件是中文阅读版；执行规则以英文 `SKILL.md` 为准。

## 用途

方案讨论被局部实现、历史命名或兼容恐惧困住时，先推荐正确的目标模型，而不是最小补丁。输出是一项高杠杆假设，以及能验证或推翻它的方法。

## 核心原则

大胆假设，小心求证。先把方向说清，再给证据路径；大胆不是把不确定性伪装成事实。

重构难度、兼容成本和现有实现是需要定价的约束，不应在目标模型出现之前替目标做决定。

## 打开格局的方法

只选一到两个能暴露当前隐含假设的方法，不要机械跑完整目录：从终局倒推、零历史包袱假设、杀掉错误概念、十倍问题、反向约束、不可妥协原则、有品位地删除、先假设再求证。需要说明或例子时读取 `references/frame-opening-moves.md`。

## 要对抗的问题

| 陷阱 | 反制 |
|------|------|
| 兼容崇拜 | 要求说出真实公共 API、持久化数据、用户承诺或合规契约；没有就不默认保留 shim |
| 局部细节陷阱 | 回到产品/架构目标、所有者、生命周期和目标边界 |
| 重构恐惧 | 先分开“正确目标”和“迁移路线”，再讨论分阶段落地 |
| 温吞答案 | 给出明确 thesis、代价、删除清单和证伪条件 |

## 工作流

1. 把问题提升到最高但仍有用的决策层：系统真正要成为什么？
2. 点名继承来的约束：兼容、迁移、旧名字、局部形状、组织习惯或模糊目标。
3. 判断约束是否真实。公共 API、持久化数据、文档化集成、用户承诺、部署与合规是真约束；内部调用、旧目录和“大 diff”本身不是。
4. 给出干净方向，以及该删、留、合、拆或重建什么；证据不足时标成假设。
5. 选择一到两个开框方法。
6. 只有选项确实不同才比较 Conservative / Clean / Staged，并推荐一个。
7. 回到执行：首个不可逆决定、首个证明点、证伪条件和暂时不要投入的事项。

## 输出

使用 `references/output-template.md`。快速方向问题压成 Thesis / Trap / Direction / Proof；较大方案或用户明确要报告时，再使用完整章节和收益账单。收益必须写具体痛点或能力，不写“更整洁”这类空泛价值。

## 路由

- 方向已定，需要落地压力测试：`goudi`。
- 判断事情是否值得做：`hai-idea`。
- 实现质量审查：`clean-code-reviewer`。
- APoSD 架构边界审查：`hai-architecture`。
- PRD：`hai-prd`。
