# Hai Naming 中文版

本文件是中文阅读版；执行规则以 `SKILL.md` 为准。

## 用途

把命名当成系统模型，而不是同义词游戏。好名字让目标读者不需要补全隐藏上下文，就能知道概念是什么、谁拥有它，以及它和邻近概念有什么区别。

## 选择模式

- **快速命名**：一个局部变量、函数、prop、文件或概念。给 3–5 个真正有区别的候选，推荐一个，简短解释决定性差异。
- **命名审计**：公共或跨模块词汇、多组关联名字、带迁移影响的改名。建立词汇图、追调用流、给按优先级排序的改名清单。

不要让一个局部变量名背负审计级的推理仪式。

## 判断规则

1. **放在上下文中命名。** 阅读声明、调用方、邻近概念、层、受众和生命周期；不能从孤立片段虚构全局模型。
2. **选择一个视角。** 产品层描述用户意图，领域层描述稳定概念，运行层描述执行责任，适配层描述跨越的边界。真实边界变化前保持视角稳定。
3. **保留决定性信息。** 只有周围表达已经携带被省略信息时才缩短。公共与跨模块名字通常需要更明确。
4. **一个概念一个词。** 同一概念保持同一术语，不同概念不要共享方便但含糊的词。
5. **命名所有权，不命名偶然机制。** `Manager`、`Service`、`Helper`、`Data`、`Info`、`Context`、`get`、`build` 只有在准确表达本项目模型时才合适。
6. **把命名摩擦当证据。** 所有候选都要一段话解释时，通常是职责或视角混在一起。先建议澄清设计，不要继续堆同义词。

公共或跨模块决策需要更完整的上下文、调用流、对称性、生命周期和迁移检查时，读取 `references/principles.md`。

## 工作流

### 快速命名

1. 写清概念、读者、所在层和最近的竞争术语。
2. 阅读用户提供的周围代码或文字。
3. 生成 3–5 个实质不同的候选。
4. 推荐一个，并说明最接近的备选为什么输。
5. 只有证据确实让命名不稳定时才指出设计问题。

### 命名审计

1. 阅读相关声明、调用方、契约、文档和持久化/wire 名称。
2. 映射行动者、概念、生命周期、分层词汇和重载术语。
3. 找出错误视角、信息丢失、旧词、碰撞和不一致。
4. 公共/API/领域名字优先于小局部变量。
5. 每个改名写 `old -> new`、证据、概念修复、影响面，以及兼容性是否由真实契约要求。
6. 把目标词汇和迁移计划分开。

## 输出与路由

使用 `references/output-template.md` 对应模式。快速回答保持自然简短；审计必须带证据和迁移范围，但不强制展示“拍脑袋”等表演性推理过程。阅读后改变主意且影响结论时，再说明变化。

- 真正问题是模块所有权或抽象：`hai-architecture`。
- 字段是否存在、存还是算：`entity-model-auditor`。
- 要的是大胆方向而不是名字：`geju`。
- 整个 React 组件 API：`react-component-diagnosis`。
