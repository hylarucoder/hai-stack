# React 组件诊断输出模板

用于输出组件架构体检报告，按组件规模裁剪。每个评分必须由具体代码证据（`文件名:行号` 或 `文件名` 中的 `函数名`）支撑——找到具体问题才扣分，给 5 分也要有值得学习的设计模式作证据。

```markdown
# 组件诊断报告：<组件名>

> <一句话概括组件职责>

## 评分卡

| 维度 | 得分 | 一句话评价 |
|------|------|-----------|
| 使用者 API | ★★★★☆ | <summary> |
| 数据流 | ★★★★★ | <summary> |
| 可测试性 | ★★★★☆ | <summary> |
| 可扩展性 | ★★★★☆ | <summary> |
| 性能 | ★★★☆☆ | <summary> |
| 心智模型 | ★★★★★ | <summary> |
| 边界契约 | ★★★★☆ | <summary> |
| **综合** | **★★★★☆ (4.1)** | <overall> |

（★ 对应 1-5 分：5 教科书级 / 4 扎实有小瑕疵 / 3 及格有改进空间 / 2 问题突出 / 1 需重写）

## 逐维度分析

每个维度列出优点和不足，引用具体代码位置（`文件名:行号` 或函数名）。
不足要说清"是什么"和"为什么是问题"，而不是笼统的"可以更好"。

## 亮点

列出 2-3 个具体的设计亮点，引用代码位置。这些是值得在团队内推广的模式。

## 改进建议

按优先级分三级：

### P0 — 值得尽快改
会导致 bug、性能问题、或维护隐患的问题。

### P1 — 建议优化
改了会明显提升代码质量或开发体验。

### P2 — 锦上添花
有则更好，不改也不会出事。

每条包含：
- **问题**：具体描述，引用代码位置（`文件名:行号` 或函数名）
- **影响**：这个问题会导致什么后果
- **建议**：怎么改，给出具体方向（但不写代码）
- **工作量**：小（< 1h）/ 中（1-4h）/ 大（> 4h）

## 架构图（可选）

如果组件有多层结构，用文本图或 mermaid 画出数据流。
```
